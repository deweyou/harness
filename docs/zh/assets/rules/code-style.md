# 代码风格

编写、修改或审查代码时使用本 Rule；如果项目级指令更具体，则以项目级指令为准。

## 默认原则

- 先遵循现有项目约定，再应用通用偏好。
- 偏好清晰、显式的代码，避免炫技或隐藏行为。
- 让改动保持局部且边界明确。
- 在可行时，避免把行为变化、重构、重命名和格式整理混在一起。

## 命名

- 名称应表达领域含义，而不是偶然的实现机制。
- 有更准确的名称时，避免使用 `data`、`info`、`item`、`temp`、`result`、
  `manager`、`helper` 和 `utils` 等模糊名称。
- 布尔值使用谓词命名，例如 `isReady`、`hasAccess`、`canRetry` 或
  `shouldPersist`。
- 不要依赖注释解释含糊的名称；应直接重命名。

## 函数

- 一个函数应在同一个抽象层级只做一件事。
- 参数应尽量少。多个值总是一起传递时，将它们建模为具名 options 对象、值对象、
  struct 或同类结构。
- 避免用标志参数让一个函数承担多种行为。
- 让重要副作用在函数名或 API 形态中可见。
- 当名称能揭示业务含义时，把复杂条件提取成具名谓词。

## 错误

- 不要静默吞掉错误。
- 区分可恢复错误和不可恢复错误。
- 在有意义的边界转换或包装错误，让调用方收到正确抽象层级的错误。
- 错误信息应有助于诊断问题，同时不能泄露秘密信息。

## 注释

- 注释应解释“为什么”，不要复述代码已经表达的“是什么”。
- 为不明显的取舍、外部系统怪异行为、兼容性约束、安全假设和刻意采用的非常规决策写注释。
- 添加解释性注释前，先改善命名和结构。
- 立即删除或更新过时注释。

## 测试

- 测试行为，而不是偶然的实现细节。
- 测试应让重构更安全，而不是冻结当前实现形态。
- 行为变化、修复缺陷或共享契约移动时，添加或更新测试。
- 可行时，在修复缺陷前先添加一个会失败的回归测试。
